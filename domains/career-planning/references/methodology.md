# Career planning — methodology

## 1. Evidence audit

| Claim                    | Artifact that proves it                        | Strength             |
| ------------------------ | ---------------------------------------------- | -------------------- |
| "Comfortable with React" | link or repo, shipped feature, years on a team | strong / weak / none |

Strength rules: shipped and observable is strong; used on a job with no artifact
is weak; self-study only is none. Plans are built from strong and weak claims,
never from "none" claims presented as skills.

## 2. Reverse-engineering the target role

Collect 8–10 postings for the exact title and market. Then:

1. Split each posting into requirements: technologies, systems, ownership level,
   domain knowledge, process (review, testing, on-call), communication.
2. Count how many postings mention each requirement.
3. Keep requirements appearing in 5 or more postings — those are the market's
   real filter, not any single company's wish list.
4. Note the two or three requirements that appear in senior postings but not
   junior ones; those are the promotion gaps.

## 3. Gap sizing

| Gap size | Meaning               | Typical fix                             | Effort  |
| -------- | --------------------- | --------------------------------------- | ------- |
| None     | provable today        | surface it in resume and interviews     | 0 h     |
| Small    | knows it, no artifact | small project or write-up               | 10–30 h |
| Medium   | needs practice        | scoped project with a real user         | 40–80 h |
| Large    | new discipline        | course plus a project, or a role change | 150 h+  |

Rank by frequency × gap size. Do the cheap high-frequency items first so the
resume improves before the long items land.

## 4. Proof artifact ladder

From cheapest to most convincing:

1. Written explanation of the concept in the user's own words (one page).
2. Small working project with a README and a demo.
3. Contribution to an existing codebase, reviewed and merged.
4. Project with a real user, plus numbers (latency, users, cost).
5. Public talk, article, or teaching material others use.
6. Ownership at work: on-call, migration, or a system the user designed.

Each plan item should name its rung explicitly.

## 5. Time budget arithmetic

State hours per week, weeks per quarter, and total available hours. Assign each
gap an hour estimate from the table above. If the total exceeds the budget,
choose what to cut rather than compressing every estimate. Never present a plan
that requires more hours than the user has.

## 6. Decision points

Examples:

- "If by <date> the target market still requires <requirement> and I have only
  the rung-2 artifact, extend the timeline by one quarter."
- "If two internal promotion conversations produce no scope change, start
  applying externally."
- "If the pivot target rejects me three times at screening, revise the target
  level rather than the technology."

## 7. Failure modes to avoid

- Planning by technology instead of by requirement frequency.
- Certificate stacking with no artifact.
- A plan that requires a role change to practise the skill it promises.
- "Network more" with no named events, people or cadence.
- Targets that mix two levels or two markets, making progress unmeasurable.
