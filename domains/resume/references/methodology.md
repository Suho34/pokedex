# Resume improvement — methodology

## 1. Bullet formula

`<Verb> <what> <scope or scale> <mechanism> <outcome>`

- Verb: built, migrated, reduced, automated, designed, debugged — not "worked
  on", "helped with", "responsible for".
- What and scope: the system and its size (users, requests, records, team).
- Mechanism: the specific approach or technology that made the difference.
- Outcome: a measured result the user supplied, or `[add number]` plus what to
  measure.

Illustrative shape only — never copy the numbers into a real resume:

```
Before: Worked on the checkout page and helped improve performance.
After:  Cut checkout page load from [add number]s to [add number]s by
        code-splitting the payment bundle and preloading the address API.
```

## 2. Requirement mapping

| Requirement from the target | Proven by           | Strength | Action                                  |
| --------------------------- | ------------------- | -------- | --------------------------------------- |
| "REST APIs at scale"        | internship API work | weak     | add scale detail if real; else gap list |
| "TypeScript"                | two projects        | strong   | keep, lead the skills line with it      |

Strength: strong = shipped and observable; weak = used but unquantified; none =
not present.

## 3. Section order for early-career applications

1. Header: name, one contact route, location, links.
2. Summary: two lines, target role plus strongest proof. Omit if it repeats the
   header.
3. Skills: only technologies with supporting evidence, grouped by area.
4. Experience: internships and jobs, newest first.
5. Projects: two or three, each with a link and one measured outcome.
6. Education.

For experienced candidates, move experience above skills and drop the summary if
the latest role already states the target.

## 4. Length and density

- Early career: one page. Experienced: two pages maximum.
- Three to five bullets for a substantial role, one or two for a short internship.
- Every line earns its space by proving a requirement for this target.

## 5. ATS safety

- Single column, no text boxes, no tables for content, no icons for meaning.
- Standard headings: Experience, Education, Skills, Projects.
- Plain .pdf or .docx as the posting requests; no images of text.
- Mirror the posting's exact term for a technology the user genuinely knows
  ("Node.js" vs "NodeJS") — no keyword stuffing beyond real skills.

## 6. Tailoring pass

1. Reorder bullets so the most relevant sits first in each role.
2. Replace generic framing with the posting's vocabulary where it is truthful.
3. Move or cut projects that do not serve this target.
4. Re-read every line and ask: could this sentence describe anyone? If yes,
   make it specific or delete it.

## 7. Changelog format

| Section             | Change                            | Requirement served        |
| ------------------- | --------------------------------- | ------------------------- |
| Experience — role 2 | rewrote 3 bullets with mechanisms | "debug production issues" |

The changelog is how the user keeps control of their own claims.
