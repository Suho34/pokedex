# Job preparation — methodology

## 1. Round map

| Stage                | What is tested                          | Drills                                                           |
| -------------------- | --------------------------------------- | ---------------------------------------------------------------- |
| Recruiter screen     | motivation, fit, salary range, timeline | 60-second background, three "why this role" reasons              |
| Hiring manager       | ownership, judgement, collaboration     | four STAR stories across conflict, failure, ownership, ambiguity |
| Technical screen     | coding fluency under time               | two timed problems in the language the user knows best           |
| Take-home            | scoping, testing, communication         | time-boxed plan, README outline, deliberate cut list             |
| System design        | structure, trade-offs, scale reasoning  | one walkthrough of a system the user has actually built          |
| Behavioural / values | self-awareness, teamwork                | the same STAR stories, shortened to 90 seconds                   |

Match the plan to the stages the user actually faces; do not train everything.

## 2. Competency matrix

| Requirement                | Story that proves it   | Strength | Prepare if none                               |
| -------------------------- | ---------------------- | -------- | --------------------------------------------- |
| "Own a feature end to end" | <project from profile> | strong   | outline one from coursework, labelled as such |
| "Debug production issues"  | none                   | gap      | say so; do not script an answer               |

## 3. STAR skeleton

- **Situation:** one sentence — team, product, constraint.
- **Task:** what the user specifically owned.
- **Action:** three or four concrete steps, naming the mechanism and the
  trade-off considered.
- **Result:** the outcome, with a number the user supplied or `[add number]` and
  what to measure.
- **Reflection:** one line on what they would do differently.

Keep the whole answer under 90 seconds when spoken. If Action is longer than
three steps, the story is probably two stories.

## 4. Question bank shape

Cover at least: one ownership story, one conflict story, one failure story, one
ambiguity story, one "proudest work" story, and one technical deep-dive on the
project listed first on the resume.

## 5. Drill design

| Drill                         | Time box | Output                                                    |
| ----------------------------- | -------- | --------------------------------------------------------- |
| Outline the answer in writing | 10 min   | five bullets in STAR order                                |
| Say it out loud, recorded     | 5 min    | one recording reviewed for filler and length              |
| Answer under interruption     | 5 min    | one follow-up question answered without restarting        |
| Timed coding problem          | 45 min   | working solution plus a written explanation of complexity |

## 6. Take-home scoping

1. Read the brief twice and write the acceptance criteria in your own words.
2. Time-box to the stated hours, and reserve the last 20% for the README.
3. Build the thinnest end-to-end path first, then deepen one area.
4. State assumptions, what was cut, and what would come next.
5. Never trade correctness for extra features.

## 7. Preparation plan table

| Date | Drill | Output | Status |
| ---- | ----- | ------ | ------ |

Fill it backwards from the interview date. If the first row starts after the
interview, the plan is wrong.

## 8. Common failure modes

- Memorised answers that collapse under one follow-up question.
- Stories with no numbers because the user never measured anything — fix by
  choosing a different story or adding `[add number]`.
- Practising algorithms for a behavioural-only loop.
- Silence on trade-offs in design rounds; answer with options and a choice.
- Asking no questions, which reads as no interest in the role.
